# Query Memory：設定與擷取接線

設定項與預設值見[設定](settings.md)；儲存與清理契約見[儲存](query-memory-storage.md)與[有界維護](query-memory-maintenance.md)。

## 整組預設關閉

`sqlAssist.queryMemory.enabled` 預設 `false`，關掉時不擷取，也不跑背景整理——整理一樣是在動
使用者的資料。自我測試 PASS 只證明存得起來，不構成替他決定的理由。另需「一般」頁的
「啟用 SqlAssist」也開著；兩者跨分類，設定頁不會跟著變灰，理由見
[設定條件式](settings-schema.md#條件式只能參照一個同分類的設定)。

## 保留分級只有日常那一級是設定

`QueryMemoryRetentionPlan` 收設定給的期限長度與配額，`BuildLadder` 以固定倍率 1／2／4 推出
整條分級；期限不縮到一天以下、配額不縮到一件。有序的多級資料放不進 Unified Settings，而拆成
「第二級幾天」的純量設定是在問一個使用者沒有依據的問題。代價：壓力下的收緊速度不可調，
要更早收緊只能把日常保留調短。

期限存成長度而不是絕對時間，每一輪重新換算。游標綁政策，所以只在巡完一輪且容量在上限內時
才重算；壓力期間沿用同一條分級，升級與游標才對得起來。

## 刻意不是設定的四件事

- **心跳與租約期限**（1 分鐘／10 分鐘）：使用者沒有依據可調，調錯只會讓遺留租約更早或永遠回收不到。
- **啟動延遲、還有工作時的提前、閒置提前的最小間隔**：由「多久整理一次」推導。使用者感覺得到的
  是整理頻率，不是這三個之間的比例。
- **背景佇列上限**（64 筆／32 MB 文字估計）：效能保險，不是偏好。
- **一次檢查幾個候選**（200）：有界維護的工作量，不是保留策略。

## 宿主接線

`Ssms22/QueryMemory/QueryMemoryHost` 依設定開關隔離儲存、背景寫入器、心跳與維護計時器。
計時器不在 UI 執行緒上；「宿主閒置」是使用者兩分鐘沒有編輯，不另外註冊殼層的閒置回呼。
一次只跑一個有界 `MaintainAsync`，還有工作只把下一輪排近一點。

程序探測 `QueryMemoryProcessProbe` 只有「PID 不存在」與「啟動時間對不上」算不在；存取被拒
一律視為還活著。`RecoveryBefore` 只在本程序真的持有心跳租約時才有值，心跳一斷就立刻換掉整條
分級，即使正巡到一半。

寫入器 fault 之後不再接收，宿主察覺就停用並留下紀錄；佇列滿與快照過大在狀態列回報，
前者整個工作階段只說一次。完整 `VACUUM` 是設定頁的手動命令，背景只做 WAL 截斷。

## 擷取訊號

| 訊號 | 來源 |
|---|---|
| 草稿 | `ITextBuffer.Changed` 重排去彈跳計時器，停止輸入設定的秒數後擷取 |
| 執行 | 殼層命令濾鏡；識別碼向 `IVsCmdNameMapping` 以 `Query.Execute` 換出來，不寫死 GUID |
| 關閉 | `ITextView.Closed`；同一筆交易保存最終版本並刪掉未存檔草稿 |

熱路徑只做一次靜態旗標讀取、記下最後編輯時間與重排計時器。SQL 全文到背景才展開——
`ITextSnapshot` 不可變，跨執行緒讀是安全的，在按鍵路徑上 `GetText()` 則是每打一個字複製一份查詢。
執行命令只記一筆就往下轉，不認領命令。

每個 `IWpfTextView` 是一個 Session。DocumentId 由完整路徑推出來，同一個檔案跨視窗、跨重啟都是
同一份；還沒存檔的查詢沒有路徑可推，每個視窗各自成一份——拿標題（`SQLQuery1.sql`）當身分會把
不同時候的兩個新查詢併成同一份。

連線內容在 SSMS 的連線事件當下記下伺服器與資料庫，擷取時只讀快取：`GetCurrentConnection()`
有 UI 執行緒相依性，實測塞住時 1908 ms，按下執行那一刻去問等於把它加在 F5 上。只留名稱，
完整連線字串、密碼與 Token 不進 Query Memory；還沒收到連線事件的視窗就是沒有連線內容。

## 尚未實機驗證

換不到 `Query.Execute` 就只有草稿與關閉會擷取，並在紀錄檔留下一行。命令名稱、擷取路徑與
設定頁本身都還沒有在真正的 SSMS 跑過，見[實機驗收](query-memory-validation.md)。
