# 物件結構提示與浮動預覽

兩個互不影響的表面：滑鼠停留的小提示，與可捲動、可複製的浮動結構預覽。
本擴充所有自建介面的外觀規則也記在這裡。

## 物件結構提示

滑鼠停留在資料表、檢視、預存程序或函式的名稱上，顯示物件種類、完整名稱、
欄位總數與前 8 個欄位的型別、NULL、PK、IDENTITY、COMPUTED。
支援方括號、雙引號、結構描述限定與暫存表名稱。

停留在別名上會顯示它所指的資料表；停留在 `u.Name` 的欄位上則顯示該欄位的
型別與屬性。限定詞確實是資料來源但查無該欄位時不顯示提示，
不會退回去猜同名的資料庫物件。

提示刻意只給一眼看得完的份量。提示視窗不能捲動也不能選取，放再多也讀不完，
所以最後一行是可點擊的**「開啟完整結構」**，看不完的那一半交給浮動結構預覽。

這條路徑在滑鼠移動的軌跡上，因此**只讀快取**：中繼資料沒命中就只顯示標題，
背景補上之後下一次停留就有內容；連線也只用已經解析好的目錄，絕不在這裡向
SSMS 詢問目前連線——那個呼叫有 UI 執行緒相依性，忙的時候會直接變成打字延遲。

## 浮動結構預覽

三條入口共用同一個視窗：建議清單開著時按**向右鍵**、滑鼠停留提示裡的
「開啟完整結構」、以及「工具 → SqlAssist → 顯示游標處物件的結構」。

| 分頁 | 內容 |
|---|---|
| 欄位 | 序號、名稱、型別、旗標徽章、計算欄位運算式、預設值 |
| 索引 | 名稱、種類、索引鍵欄位與排序、INCLUDE 欄位、篩選條件 |
| 外來鍵 | 名稱、欄位對應、ON DELETE／ON UPDATE 動作 |
| 參數 | 模組類物件的參數與 OUTPUT 標示 |
| 指令碼 | 可直接執行的完整 CREATE 指令碼，有 T-SQL 語法著色 |

空的分頁不會出現。摘要就寫在物件名稱底下，例如
`23 個欄位　PK：Id ASC　3 個索引　1 個外來鍵`——那是「這個物件有多大」的一部分，
該跟名字待在一起。底部那一條留給操作之後的回饋（例如「已複製選取的儲存格」），
平常是空的。

### 外觀

版面的原則是**用留白分層，不用線條**。整個視窗只剩兩條細線：欄位標題的下緣，
與外框。其餘層次靠間距與極淡的底色，而那些底色是從**前景色**按比例調淡算出來的，
不是從主題裡挑現成的筆刷——現成的筆刷是為停駐面板調的，放在提示視窗的底色上
不是太重就是看不見，而且淺色與深色主題各偏一邊。從前景色調淡則兩種主題自動
各自成立：淺色得到淡灰，深色得到淡白，對比永遠是同一個量。

| 元素 | 做法 |
|---|---|
| 標題 | 物件種類換成圖示，結構描述壓成淡色，只有物件名是正常字重 |
| 分頁列 | 分段控制器：一條圓角底槽，選到的那一段浮起來，而不是五個方框 |
| 欄位表 | 沒有格線，奇數列墊一層 4.5% 的底色 |
| 旗標 | `PK`、`NOT NULL`、`IDENTITY` 收成一欄膠囊徽章，欄數從八降到六 |
| 按鈕 | 沒有邊框，滑鼠移上去才長出底色 |
| 出現 | 120 毫秒淡入，只用 ease-out、不回彈 |

字級只有 `preview.fontSize` 一個旋鈕（預設 14，範圍 9 到 20），其餘六個字級與
行高都由它推導：標題大一號，摘要與欄位標題小一號，徽章再小一點。讓使用者自己
維持這些比例，是把版面設計的工作丟給他。

**指令碼分頁不受這個值影響**——它跟的是編輯器的字型與字級（向分類外觀對應表
借的）。那一份文字是要拿去跟查詢視窗裡的程式碼對照的，兩邊字級不一樣反而難讀。

改完設定不必重開查詢視窗，下一次展開就是新的字級。

旗標**只標例外**：可為 NULL 是 SQL 的預設，因此不給徽章——沒有徽章就是可為 NULL。
強調色整個視窗只有主索引鍵用得到；多給一個，強調就不再是強調。

淡入刻意只做透明度而不做縮放：承載視窗的大小是平台按內容量出來的，縮放只會讓
內容縮進去而視窗不動，四周露出一圈承載視窗的底色，那比不做動畫還糟。

交替底色只能走資料格自己的 `RowBackground` 與 `AlternatingRowBackground`。
`DataGridRow.Background` 是**轉移屬性**，資料格會把自己的值蓋到每一列上，
優先權高過任何樣式與觸發程序——改用觸發程序畫交替列的結果是每一列都沒有底色。

### 同一套外觀用在整個擴充

上面那些不是浮動預覽專屬的。字型、字級推導、按鈕、輸入欄位、核取方塊、清單列與
資料格樣板全部集中在 `SqlAssist.Ssms22/UI/SqlAssistChrome.cs`，是本擴充所有自建
介面的**唯一**外觀來源；程式碼片段對話框用的就是同一份。分成兩份的話，改一邊
忘了另一邊的症狀是「兩個視窗長得像但又不完全一樣」，那比一開始就不統一更難看。

留在 `Preview/PreviewChrome.cs` 的只剩別的視窗用不到的三樣：出現時的淡入、
物件種類的圖示，以及欄位表的旗標徽章。

對話框刻意不跟著 `preview.fontSize` 走，固定用同一個基準值（14）。那個設定是為
浮動預覽開的——它貼在程式碼旁邊，要跟編輯器的字級一起讀；而且它在預覽關閉時
是停用狀態，讓一個停用的設定影響另一個視窗只會讓人找不到原因。

核取方塊也自己畫。內建的那一個跟的是 Windows 佈景主題而不是 SSMS 的，
SSMS 深色主題裡會出現一個白底方框浮在暗色面板上。

### 為什麼不是工具視窗

視窗掛在編輯器自己的**空間保留管理員**上，也就是 IntelliSense 清單與提示視窗
用的那一套機制，並且排在內建的 `completion` 之後。這帶來三件單靠 WPF `Popup`
做不到的事：

- **位置由平台計算**：自動避開建議清單已經佔住的空間，撞到螢幕邊界就翻到
  另一側，不必自己量清單有多寬。
- **點進去不會關掉清單**：焦點落在這種視窗裡時，編輯器仍然算「持有焦點」，
  所以可以用滑鼠把 `CREATE TABLE` 整段拉選起來，建議清單不會消失。
- **跟著編輯器走**：捲動、切換視窗、關閉查詢視窗時一起處理掉。

### 擺放位置

| `preview.placement` | 行為 |
|---|---|
| `beside` | 貼在建議清單的左右任一側，優先右側、撞到邊界才翻 |
| `stacked`（預設） | 擺在建議清單的上下方，從清單錨點延伸到編輯器右側 |

`beside` 的落點完全交給平台，離清單多遠、落在左側還是右側都是它算的——
**建議清單為自己的說明提示保留的空間也算在內**，所以視窗有時會被推得比看起來
該有的位置更靠外側，寬度較窄時也可能整個翻到左側蓋住物件總管。
`ISpaceReservationAgent` 只有 `PositionAndDisplay(Geometry)`，那是「重新定位」
而不是「回報位置」，呼叫它會有副作用；沒有任何公開 API 可以查詢落點、
鎖定側邊或把視窗往右推。

打開 `diagnosticsEnabled` 之後，每次顯示都會在記錄檔留下一行落點資訊
（哪一側、視窗的螢幕座標範圍、錨點位置、編輯器寬度），那是唯一能看出
平台為什麼這樣擺的地方。

一百多個欄位的資料表在 620 寬裡永遠要橫向捲，位置也不穩定，那就改用
`stacked`：左側跟建議清單使用同一個文字錨點，右側不超過編輯器，欄位表也能
一次攤開好幾欄，代價是會蓋住上下幾行程式碼。

`stacked` 尚未手動調寬時會自動延伸到編輯器右側；拖曳握把後則記住獨立的
stacked 寬度，不會覆蓋 `beside` 的尺寸。水平拖曳的最大值會跟著錨點與編輯器
右界重算，所以一般情況下拖不出編輯器；唯一的例外是錨點本身已經很靠近右界，
那時保底到最小寬度 320，寧可讓平台把視窗往左推，也不要交出一個窄到看不了的
視窗。編輯器的縮放比例也會換算進去，放大字級的人不會拿到一個偏窄的視窗。
高度與 `beside` 走同一條規則，上限是編輯器的 80%；要遮掉多少行程式碼是
使用者自己的取捨。

### 為什麼沒有圓角

試過請 **DWM** 用 `DWMWA_WINDOW_CORNER_PREFERENCE` 把承載視窗裁成圓角
（WPF 這一層做不到：空間保留機制的 `Popup` 是平台建立的，拿不到它就無法在開啟前
設 `AllowsTransparency`，沒有透明度時 `CornerRadius` 只會在角落留下方形底色）。

實際跑起來的結果是：**第一次彈出正常，換一個清單項目之後視窗外圈多出一圈
灰色的框**。原因是承載視窗本來就比內容大一圈，平常沒有被繪製所以看不見，
而一旦把它交給 DWM 當成有圓角的視窗管理，那一圈就被畫出來了。第一次正常則是
因為那時承載視窗還沒建立，設定根本沒送出去。滑鼠停留開啟的預覽每次都是全新的
承載視窗，所以從來不會出現這個現象。

沒有公開 API 可以要求平台把 `Popup` 建成透明的，也沒辦法讓內容填滿承載視窗，
因此圓角整個移除了。方角配一條細邊框，至少每一次看起來都一樣。

顯示時**不會主動搶焦點**，游標留在編輯器裡，可以繼續打字；滑鼠滾輪不需要焦點
就能捲動，要拉選文字時點一下才把焦點交出去。

### 操作

| 按鍵／動作 | 行為 |
|---|---|
| `→` | 建議清單開著時展開預覽；沒有清單時照常右移游標 |
| `↑` `↓` | 展開狀態下跟著選取換內容，維持展開 |
| `←` | 展開狀態下收合；沒展開時照常左移游標 |
| `Esc` | 收掉預覽（清單開著時就照常先關清單，預覽跟著收） |
| `Tab` `Enter` | 挑選完成，預覽跟著關 |
| 滑鼠拉選 ＋ `Ctrl+C` | 複製選取的內容 |
| 標題列按鈕 | 複製選取／複製全部，不受鍵盤焦點影響 |
| 右鍵 | 複製選取內容／複製整個表格／複製完整指令碼 |
| 角落握把 | 拖曳調整大小，尺寸會寫回設定檔 |

指令碼分頁是一個唯讀的 `RichTextBox`，著色用的是本擴充自己的詞法分析器，
字型與顏色則向編輯器的分類外觀對應表借，所以跟得上 SSMS 目前的佈景主題。

這裡刻意**不**內嵌真正的編輯器：內嵌編輯器雖然能拿到免費的著色，
但它會把鍵盤焦點搬進另一個呈現來源，編輯器因此判定自己失去聚合焦點，
整個浮動視窗會在使用者點下去的那一刻被平台收掉——同一個視窗裡的資料格分頁
完全沒有這個問題，差別就在這裡。

複製一律走明確的處理常式與標題列按鈕，不依賴 `ApplicationCommands.Copy` 的繞送：
浮動視窗是自己的一個承載視窗，拿不到鍵盤焦點，命令繞送不到就會變成
「選得起來但複製不了」。資料格分頁以儲存格為選取單位，只選幾欄就只複製那幾欄。

`Ctrl+C` 也因為同一個理由收不到，所以改由查詢視窗那一端的命令處理常式轉過來：
編輯器自己沒有選取、而預覽裡有選取時，這個命令就交給預覽。
選取的顏色則開了非作用中高亮，否則沒有焦點的視窗裡選起來是看不見的。

指令碼是可以直接執行的：主索引鍵寫進 CREATE TABLE 的條件約束，
唯一條件約束寫成 ALTER TABLE，計算欄位寫成 `AS 運算式`。

### 不卡頓的做法

- **視窗預先建好**：建議清單第一次開啟之後，以 `ApplicationIdle` 優先權在背景
  把整棵 WPF 樹建起來——那是兩次按鍵之間 UI 執行緒真的沒事做的時候。
- **沒展開就不做事**：方向鍵掃過二十項時，預覽只記下選到誰，不畫也不查。
- **由便宜到昂貴**：第四層快取命中就直接畫完；只有第二層命中就先畫欄位、
  索引與外來鍵稍後補上；兩層都沒有才先畫標題並啟動節流計時器。
- **節流**：換選取後預設等 220 毫秒才真的查資料庫，按著方向鍵一路往下時
  中途的每一項都不會送出查詢。
- **只填看得見的分頁**：五個分頁一起填等於每換一個物件就多四次版面計算，
  切過去時再填。

### 調整大小為什麼不用一般的做法

握把回報的位移量是相對於它的父代算出來的，而浮動視窗在調整大小的過程中會被
平台重新定位——父代自己在動，位移量就把視窗的移動誤算成滑鼠的移動，
於是「變大 → 視窗被移走 → 又算出一段位移 → 再變大」，形成回授而亂跳。
因此改成每一步都直接問系統游標的絕對座標，尺寸成為「起始尺寸 ＋ 游標位移」
這個純函式，視窗怎麼移動都不影響算出來的大小；拖曳期間也不請平台重新定位，
放開手才收斂一次。

握把還會自己換邊：視窗貼在錨點左側時，平台釘住的是它的右邊界，加寬會往左長，
握把留在右下角就會出現「往右拖曳、左邊界卻往外跑」。
