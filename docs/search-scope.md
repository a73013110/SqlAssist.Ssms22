# SQL Search 的範圍

工具窗上兩顆按鈕決定這一輪搜哪裡：伺服器與資料庫；左邊那一顆圖示鈕把兩者一次換回查詢視窗
（與 SQL Memory 同一顆，規則見[視窗骨架](ui-windows.md#輸入列與範圍列)）。契約與 provider 見
[SQL Search](search.md)。

這三顆是工具列範圍層（搜尋列上面那一層）的**第一群**。範圍層依問題分三群：`查詢視窗 伺服器 資料庫`（搜哪裡）｜`種類`（搜什麼）｜
`名稱 內容 欄位`（比對哪裡）。每一顆之間都看得到線，而群間那一條比群內的高一截、寬一截，
兩級的規格與換行規則見[篩選](ui-filters.md#分隔線與換行)：全部畫成同一種的那一版，
使用者會把種類讀成第三個範圍條件。列首與分段開關換到第三列時它前面那一條都收起，
不留一條開頭的孤線。

## 兩顆按鈕跟著誰

伺服器單選：跟著作用中的查詢視窗（預設），或指名物件總管上已連線的一台。換一台換的是整份
目錄，不是加一個條件。資料庫是多選，沒有指名時就是這條連線的那一個。

摘要一定說得出目標：伺服器是 `查詢視窗（LIBSQL01）`、`查詢視窗（未連線）`；資料庫跟著查詢視窗時是
`查詢視窗（LibArchive）`，指名了別台時是 `連線預設（master）`，沒有連線時是`未連線`。
只寫「查詢視窗」與「連線預設」的症狀是使用者盯著兩顆看起來正常的按鈕，而下面那一句是「尚未連線」，
或他確定存在的物件搜不到——因為物件總管那條連線的預設資料庫通常是 `master`，而他以為自己在搜整台。
跟著查詢視窗時資料庫也說「查詢視窗」：那時搜的就是查詢視窗連著的那一個，換分頁也跟著換，
與伺服器那一顆、SQL Memory 的「查詢視窗」段同一句話。

每一句字只有一份：「查詢視窗（…）」是 `SqlEditorConnectionText.Label`，資料庫那一句是
`ConnectionDefaultSummary`，摘要與面板第一列兩處不會說得不一樣。括號裡的名稱由
**開啟後的連線**（`IDbConnection.Database`）說了算，不從連線字串推——物件總管那條上沒有初始
目錄，所以它要等資料庫清單回來才補得上，在那之前不帶括號，不猜一個名字。

指名一台伺服器之後**直接把資料庫面板打開**：那條連線的預設資料庫通常是 `master`，而
「搜整台的 master」幾乎不是使用者要的範圍。下一步擺在眼前比讓他自己發現範圍不對便宜，
而那一次展開同時問到了預設是哪一個。換回查詢視窗時不開——那條連線的資料庫就是他正在看的那個。

## 什麼時候重讀範圍

切換分頁（`ActiveSqlEditor.Changed`），以及同一個分頁裡換連線、換資料庫或中斷
（`SqlEditorConnectionWatcher.Changed`），都會重讀範圍並重算清單上每一列。只接前者的話，
在原分頁改連別台之後，列上與摘要都還是上一台。後者每批 F5 都發一次，所以只有範圍真的換了
（目錄快取鍵或伺服器不同，由 `SqlSearchProviders.UseConnection` 回答）才作廢結果重搜，
否則按一次 F5 清單就閃一次。預覽的定義快取不跟著清：它的鍵是那一筆自己的伺服器、資料庫與編號。

**先確認再讀**（`SqlSearchCatalogs.ConfirmAsync`）：連線事件只在中繼資料服務上立旗標，
事件當下它手上的目錄還是上一台的。每一輪搜尋與每一次連線變更都先等確認，否則換台後
第一輪搜的是上一台，之後也沒有事件再叫它重搜。

**目錄與伺服器一次交出**（`SqlSearchConnection`，服務端是 `PeekCurrentConnection`）。
伺服器另外問 SSMS 的版本，在確認前那一段拿到新的一台配上一台的目錄：清單列著上一台的物件
卻標成新的一台，在物件總管中選取找不到，移至定義還會沿用錯的連線。

**換到另一台就清掉勾選的資料庫與清單**（`SqlSearchBrowserModel.ObserveServer`）。規則掛在
「換了台」上，不掛在指名伺服器那個操作上，否則跟著查詢視窗換台、指名的那一台消失時，
會拿上一台的名稱搜這一台，每個都回「不存在」。斷線不算換台。

## 資料庫清單從哪裡來

走 `SqlCatalogSearchDatabases.TryList`，在面板展開時才問。**不**讀
`SqlMetadataCatalog.CachedSnapshot`：那一份是補全在按鍵路徑上載入的，指名物件總管上一台
伺服器時它從頭到尾是空的——下拉一個選項都沒有，而整輪只搜連線預設的那一個。

展開下拉**就是**使用者在要求這份清單，所以那一刻去問資料庫是對的；禁止的是在沒有人打開它的
時候先問（每個查詢視窗一次）。清單不建任何索引，索引只發生在真的勾了某一個之後。

沒有指名任何資料庫時，這一輪搜的是這條連線的預設資料庫，而它叫什麼同樣由**開啟後的連線**說了算
（`SqlCatalogSearchIndex` 與清單共用這條規矩）。照連線來源那一份走的版本在物件總管那條連線上拿到空字串，
而索引的建構子不收空名稱——那個 `ArgumentException` 不是 `DbException`，降級接不住，畫面上變成
「『catalog』這一輪失敗：資料庫名稱不可為空。參數名稱: databaseName」，一句使用者完全無從下手的話。

一份快取只留目前這條連線；換連線在**連線觀測**那一刻就同步（`SyncTo`），不是等到展開下拉才比對——
比對藏在重問裡的那一版，換一台之後「問過了」仍是上一台的答案，宿主據此提早收工，下拉從此畫著
上一台的資料庫，而且不會自己好。按「重新整理」也重問。問不到時**留住上一份**並在清單上方
說一句，不清空：清空等於說「這台伺服器上一個都進不去」，而那與「這一次問不到」是兩件事，
下一步也不同。已經勾起來的名稱一律列得出來，就算不在這一份清單裡，否則使用者取消不掉自己剛選
的條件。實作在 `Ssms22/Search/SqlSearchScopeDatabases.cs`。

清單還在路上時面板先說一句（`SqlBusyNotice`），不先給一份空的：空面板與「這台上一個都沒有」
在畫面上一模一樣，而使用者會關掉它去別的地方找。

## 沒有連線時的出口

狀態表面帶一顆按鈕（`SqlSurfaceState.ActionLabel`）：跟著查詢視窗而沒有連線時是
「從物件總管挑一台」，指名的那一台連不上時是「回到查詢視窗」。兩種狀態互斥，所以按鈕只有一顆。
只說一句話而把出口留在別的選單裡，等於要使用者先猜出問題出在範圍上。

**不**自動退回物件總管：那個服務第一次取用會把它的工具視窗叫出來，而使用者可能正是把它關掉
的人，所以這一步一定由他發動。只有一台時直接用它——那不是替他猜，清單上只有那一個答案；
好幾台就打開同一份伺服器面板讓他挑，理由與 `SqlSearchCatalogs.DropMissingServer` 相同：
默默換掉使用者的範圍比留著更糟。

## 關掉重開不記得的那幾項

伺服器、資料庫與物件種類**不記**。前兩者綁在一條連線上：記住之後換一台，工具窗會與作用中的
查詢視窗脫鉤，或對一個不在這台上的資料庫每一輪都回報「讀不到」。種類是一次調查裡的收斂，
不是長期的工作方式；記住它的症狀是下星期打開視窗搜 `Loan`，那張表因為上次勾過別的種類而不在。
記得的那三項見[SQL Search](search.md#關掉重開記得什麼)。
