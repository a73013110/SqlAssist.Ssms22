# 結果導航

一筆搜尋結果點下去會發生什麼：兩條路各自的可用條件、節點位址怎麼組，以及不准做的事。
排名、合併與 provider 契約見 [SQL Search](search.md)，F12 那條路徑自己的開窗與執行緒分工見
[移至定義](go-to-definition.md)。

## 兩條路只成立一邊是常態

**移至定義**把定義開進沿用連線的新查詢視窗，**在物件總管中選取**把樹展開到那個節點上。
前者要「查詢視窗那條連線就是這一筆的來源」，來自別台伺服器時它擋下來；後者要「樹上有
這一台」，指名別台時它正好還在。共用一個判斷的症狀是指名伺服器之後，一列結果什麼都做不了。

前者問的是**是不是同一台**（`SqlSearchCatalogs.SharesActiveEditorServer`），不是「有沒有
指名伺服器」（`FollowsActiveEditor`，那是範圍的狀態，給下拉的勾與按鈕摘要用）。兩者答案
常常不同：使用者從物件總管指名的，十之八九正是查詢視窗已經連著的那一台。拿後者代答的
症狀是兩邊明明同一台，移至定義卻回一句「請先把查詢視窗連到那一台」，而使用者看著自己
剛連好的視窗，沒有任何辦法讓它閉嘴。比對只問伺服器、不問資料庫，而且沿用
`IsSameServer`——伺服器名稱的寫法全專案只有那一份。

辨識酬載型別仍然只發生在 `SqlSearchActivation`：多一條路是多一支方法加一個 `is` 分支，
清單樣板、圖示與預覽一個字都不改。那個類別切成兩半，純判斷那一半零 VS 相依，
清單列與樣板的回歸測試才編得進來。

一列做得到什麼**只算一次**，算在 `SqlSearchRow` 上：右鍵選單與停駐時那一排圖示讀同一個值。
兩處各算一次的症狀就是選單上已經變灰、停駐時的同一顆卻按得下去，按了只得到一句
「這一筆沒有…」。做不到的操作**變灰不收起**——收起來會讓同一列的圖示位置隨內容變，
而使用者是照位置按的。

## 節點位址

由 `Metadata/Model/SqlObjectExplorerUrn` 組，路徑照 SSMS 自己的 `sqlexplorerhier.xml`
（節點的 `Xpath` 與 `UrnShell`）。伺服器那一段沿用物件總管節點自己的 `RootUrn`，**不**自己拼
`Server[@Name='…']`：具名執行個體與有別名的連線上，連線字串裡的名稱與樹上那一行不一樣，
拼出來的位址對不上任何節點，而導航只回得出 false。

跟著查詢視窗時要反過來在樹上找那一台，比對走連線字串裡的伺服器名稱（與伺服器下拉
「同一台不列兩次」共用一份）。找不到就說找不到，**禁止**拿樹上任何一台頂替：頂替會跳到
另一台伺服器上同名的物件，而畫面上看起來完全正常。

結構描述缺了就不組位址，不省略那一段——同名不同結構描述在一個資料庫裡是常態，少了它會
停在第一個同名的節點上。三種函式共用 `UserDefinedFunction`，物件總管沒有把它們分成兩種節點。

## 掛在父物件底下的那幾種

觸發程序與條件約束在樹上**有**自己的節點，只是畫在父物件底下。一筆結果身上只有自己的
`object_id`，所以位址要先問一趟目錄（`SqlMetadataCatalog.GetParentAsync`）。那是**一條查詢**，
不載入父物件的結構：跳到一個條件約束不需要知道那張表的索引與外來鍵長什麼樣子。

| 這一筆是 | 樹上的那一段 |
|---|---|
| 資料行命中 | `Column[@Name='…']` |
| 觸發程序 | `Trigger[@Name='…']` |
| `CHECK` | `Check[@Name='…']` |
| 外來鍵 | `ForeignKey[@Name='…']` |
| 主索引鍵、唯一鍵 | `Index[@Name='…']` |
| `DEFAULT` | `Column[@Name='資料行']/Default[@Name='…']` |

後兩列各有一個容易寫錯的地方。主索引鍵與唯一鍵在「索引鍵」資料夾裡，而它們是**索引**。
`DEFAULT` 有三件事都違反直覺：**位址**掛在資料行底下（那個資料行名稱只有目錄答得出來，
同一條查詢的最後一欄）；**畫**它的卻是資料表的「條件約束」資料夾，所以 `OwnerUrn` 是那張表
而不是那一行；而且它**帶名稱鍵**，儘管一個資料行只有一個。位址是 SMO 列舉器給的，
`DefaultConstrain.xml` 接 `inc_constraint.xml` → `inc_urn.xml`，那一份對所有具名物件一律組成
`父位址/型別[@Name='…']`。三件事各自錯了都很安靜：第一個候選對不上，於是每次都退到下一個，
畫面上選到的是**那個資料行**，看起來就像功能只做到一半。

**資料行命中停在那一行上**，不是整個物件——使用者搜的是 `CopyNo`，樹上就有那一行。
這與移至定義相反，那一條的目標永遠是整個物件，因為指令碼沒有「只開一個資料行」這回事。

## 導覽服務下不到資料表底下那幾層

SSMS 的 `IObjectExplorerNavigationService.NavigateToUrnAsync` 只認得四種中間資料夾
（`Databases`、`UserTables`、`Views`、`UserProgrammability/StoredProcedures`）。位址再深
一段時，它展開父節點之後只比對父節點的**直接**子節點，而資料表的直接子節點全是資料夾，
一個都比不中，接著查那張寫死的對應表，查不到就回 false。所以單靠它時，條件約束、觸發程序、
索引與資料行**一律停在資料表上**——只有使用者先前自己展開過那個資料夾時才成功，
因為那時整棵樹的遞迴比對找得到現成的節點，看起來又完全正常。

根本原因是**資料夾在樹上沒有自己的位址**：它的 URN 就是父物件的。「用一個 URN 從樹根指到
節點」這件事因此對掛在資料夾裡的那幾種不成立，導覽服務的三支公開方法都改變不了這一點。

所以 `TryNavigateAsync` 依節點的 `OwnerUrn` 分兩段：空的由導覽服務直接指（物件本身、作業），
有值的先 `NavigateToUrnAsync(OwnerUrn)` 展開到父物件，再從那個節點往下找。第二段只做外科
手術式的那一小塊：拿父物件的 `INavigableItem` 往下走兩層（物件→資料夾→節點），資料夾靠
「`Context` 與父節點相同」認出來，而這一條同時把搜尋**關在這個物件底下**。找到就
`SynchronizeTree`，它會把沿路的節點補進樹裡、叫出視窗並選取。

**禁止**改用 `FindNode(節點位址)` 一次到底。那一支確實下得到任何一層，代價卻是從樹根開始的
全樹搜尋，而每下一層都會把沿路資料夾的子節點**建出來**——那就是向伺服器查詢。節點已經建好時
它是字典查詢所以很快；沒建好的那一次會一路翻進資料庫底下每一個資料夾，再翻進伺服器底下的
安全性、複寫、管理與 Agent，大的伺服器上是幾分鐘起跳。症狀不是「找不到」而是**那一則
「在物件總管中選取」停不下來**，而 `_selecting` 這一關讓按鈕從此按不動。

往下找那一段會查詢，所以它在背景執行緒上跑，**深度與時間都要有上限**（兩層、15 秒），
`SynchronizeTree` 才回 UI 執行緒。逾時當成找不到，呼叫端接著試下一個候選（父物件），頁尾
照實說「已改為選取…」；放掉的工作不必收，它只是把節點建出來，下一次按就是現成的。

## 候選由精確到寬鬆

每一支都交出一串候選，依序試到第一個指得到的為止，並在頁尾說出停在哪一層
（「已改為選取資料行 DueDate」）。這不是在猜寫法，而是承認樹上不一定有那個節點：使用者
可能設了篩選器，那個版本也可能沒有那一種節點。只交出最精確的那一個時，症狀是條件約束
一律說「找不到」，而它所屬的那張表就在旁邊；默默當成功則更糟——使用者以為自己正看著
那個條件約束，而選取的是整張表。

## 只准由使用者發動

導航會把物件總管的視窗叫出來、搶走焦點，展開節點還要向伺服器問資料，大的資料庫上是
好幾秒。所以這條路徑**禁止**掛在選取變更或任何輪詢上，理由與 `SsmsObjectExplorer` 上
那一條相同——使用者可能正是把物件總管關掉的人。

它也**不**走 `SqlAssistPlatformGuard` 的收斂：使用者是自己按的，安靜地什麼都不做等於故障。
每一種失敗都寫進工具窗頁尾，而且各寫各的——樹上沒有這一台、問不到父物件、節點全都指不到，
三句的下一步完全不同。

## 執行緒分工

這一條路徑要等一次目錄查詢，再回頭呼叫一個只在 UI 執行緒上成立的宿主服務。

| 階段 | 執行緒 | 做什麼 |
|---|---|---|
| 1 | UI | 挑物件總管上那一台、解析目錄（`SqlSearchCatalogs` 的解析都是 UI 親和的） |
| 2 | 背景 | 問父物件是誰（只有觸發程序與條件約束走得到） |
| 3 | UI→背景→UI | 依序導航（畫在父物件底下的那幾種，背景再往下找一層），把結果寫進頁尾 |

第 2 段由 `SqlMetadataCatalog.GetParentAsync` 自己讓出執行緒（它內部就是 `Task.Run`），
接線層**不**再包一次：多包一層只是多排一次工作，UI 執行緒一樣沒有停在查詢上。

**UI 親和性由被呼叫的那一端自保，不靠上游交還。** `SsmsObjectExplorer.TryNavigateAsync`
進場就 `SwitchToMainThreadAsync`，因此呼叫端在哪一條執行緒上都成立。反過來寫——
被呼叫端在回傳前切回 UI 執行緒——是**擋不住**的：續程落在哪裡由呼叫端的 `await` 決定，
一個 `ConfigureAwait(false)` 就把它作廢（UI 執行緒上有 Dispatcher 的同步內容，
續程不准內聯，只能排回執行緒集區）。這種錯又**只在中間真的 await 過的路徑上發作**：
資料表與檢視同步算完候選、續程原地跑，看起來完全正常，只有條件約束與觸發程序
丟 `TryNavigateAsync must be called on the UI thread`。

已經在 UI 執行緒上時那一步是同步完成的，不排訊息也不讓出執行緒，所以自保不花錢。
代價只有一個，要記在呼叫端：**禁止**用 `JoinableTaskFactory.Run` 之類的方式同步等它，
UI 執行緒被擋住時切回去的那一步永遠等不到。同步的 `TryList` 與
`TryCreateConnectionSource` 套不上這一招——同步方法切不了執行緒，那兩支維持 assert。

需要把續程留在 UI 執行緒時**明寫 `ConfigureAwait(true)`**，不要留空：這個專案滿是
`ConfigureAwait(false)`，留空的那一個看起來像漏掉的，下一個人會順手補上 `false`。
